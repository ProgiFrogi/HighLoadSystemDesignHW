# ADR-002: PostgreSQL + PostGIS — единый source of truth, без отдельного search-движка на Day 1

- Статус: Accepted
- Дата: 2026-04-23

## Контекст

Каталог должен поддерживать поиск по названию, кухне, расстоянию, рейтингу и времени доставки. При этом по исходным расчетам ресторанов порядка 20k, среднее меню — около 50 позиций, бюджет ограничен, команда маленькая.

## Альтернативы

1. **PostgreSQL + PostGIS + pg_trgm**
   - Плюсы: одна операционная система хранения, ACID, удобные join'ы, geospatial индексы, меньше DevOps-нагрузка.
   - Минусы: возможности полнотекстового ранжирования хуже, чем у dedicated search engine.

2. **PostgreSQL + Elasticsearch / OpenSearch**
   - Плюсы: отличный полнотекстовый поиск и релевантность.
   - Минусы: двойная запись / индексирование, дополнительный контур эксплуатации, выше стоимость владения.

3. **MongoDB с геоиндексами**
   - Плюсы: гибкая схема.
   - Минусы: слабее transactional-модель для заказов/платежей; каталог и заказы пришлось бы разводить по разным стекам.

## Решение

На первом этапе выбираем **PostgreSQL 16 + PostGIS** как системное хранилище для каталога, заказов и платежей.

- для поиска по названию используем `pg_trgm`;
- для расстояния и зоны доставки — `PostGIS`/`GiST`;
- для самых горячих read-path — Redis-кэш;
- отдельный OpenSearch вводим только при достижении порогов по p99/CPU или при явной потребности в более сложной релевантности.

## Последствия

### Положительные

- ниже стоимость владения;
- проще обеспечить консистентность между каталогом и транзакциями;
- быстрее старт разработки.

### Отрицательные

- поиск и ranking будут беднее, чем с dedicated search engine;
- возможна будущая миграция на dual-store схему при росте нагрузки или product requirements.
