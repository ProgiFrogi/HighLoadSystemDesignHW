# ADR-001: Выбран гибридный архитектурный стиль SBA + EDA

- Статус: Accepted
- Дата: 2026-04-23

## Контекст

Нужно выдерживать до 35k RPS в пике, быстро масштабироваться в обеденный пик, не терять платежи и при этом уложиться в ограниченный бюджет и команду из 5 человек.

## Альтернативы

1. **Модульный монолит**
   - Плюсы: минимальная операционная сложность, дешево.
   - Минусы: слабая изоляция отказов, сложно независимо масштабировать горячие контуры (поиск, статус, уведомления), тяжелее эволюционировать партнерские и пользовательские API.

2. **Мелкозернистая MSA**
   - Плюсы: сильная изоляция, независимое масштабирование, clear bounded contexts.
   - Минусы: слишком большая операционная цена для команды из 5 человек, рост сетевых hop'ов, сложность observability и локальной разработки.

3. **Чистая event-driven архитектура**
   - Плюсы: хорошо подходит для fan-out и фоновых обработок.
   - Минусы: неудобна для критичного sync user-flow: поиск -> заказ -> оплата, где нужен короткий latency budget и понятная транзакционная граница.

## Решение

Выбираем **гибрид Service-Based Architecture + Event-Driven Architecture**:

- снаружи — coarse-grained REST API через API Gateway;
- внутри — 5 доменных сервисов: Catalog, Order, Payment, Tracking, Notification;
- критичный путь пользователя остается синхронным и коротким;
- побочные действия и fan-out переводятся в события через Kafka/Redpanda.

## Последствия

### Положительные

- проще эксплуатировать, чем full MSA;
- можно независимо масштабировать горячие сервисы;
- отказ Notification/Tracking не блокирует оплату;
- удобный путь к дальнейшему разделению сервисов по мере роста.

### Отрицательные

- часть интеграций становится eventual consistent;
- нужно поддерживать контракты событий и ретраи;
- потребуется хорошая трассировка запросов и correlation-id.
