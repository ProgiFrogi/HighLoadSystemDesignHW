# ADR-003: Идемпотентные write API + transactional outbox для заказов и платежей

- Статус: Accepted
- Дата: 2026-04-23

## Контекст

Ключевое требование заказчика: **платежи не должны теряться**. При этом внешние платежные провайдеры могут таймаутить, а внутренние события по заказу и уведомлениям должны доставляться надежно.

## Альтернативы

1. **Dual write: сначала БД, потом Kafka / наоборот**
   - Плюсы: просто на бумаге.
   - Минусы: при сбое между двумя записями получаем потерянные события или фантомные платежи.

2. **Синхронный fan-out HTTP после коммита**
   - Плюсы: меньше инфраструктуры.
   - Минусы: высокая связанность, длинный latency path, каскадные отказы.

3. **Transactional outbox + idempotency keys + reconciliation**
   - Плюсы: надежная публикация событий после коммита, безопасные повторы, защита от дублей.
   - Минусы: нужен relay/outbox worker и отдельная логика reconciliation.

## Решение

Выбираем:

- `Idempotency-Key` для `POST /orders` и `POST /orders/{id}/payments`;
- таблицу `payments` с уникальными ключами `idempotency_key` и `(provider, provider_payment_id)`;
- `outbox_events` в PostgreSQL и relay в Kafka;
- reconciliation worker для кейсов `payment_pending_confirmation` после таймаута PSP.

## Последствия

### Положительные

- write API можно безопасно ретраить;
- события не теряются между БД и шиной;
- проще расследовать спорные кейсы по платежам.

### Отрицательные

- больше служебной логики и фоновых воркеров;
- нужно хранить историю попыток оплаты и статусы reconciliation.
